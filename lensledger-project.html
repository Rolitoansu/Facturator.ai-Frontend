01 — El Problema

¿Por qué LensLedger?

La gente no lleva control de sus gastos, no por falta de voluntad, sino porque registrarlos es tedioso. Las apps actuales requieren introducir datos manualmente. LensLedger elimina esa fricción con una sola acción: subir una foto.

El usuario fotografía cualquier ticket, recibo o extracto. El sistema procesa la imagen con OCR, extrae importe, comercio, fecha y categoría automáticamente, y lo añade al historial financiero. Cero formularios. Cero importaciones manuales. Cero CSV.

Portfolio que se demuestra en 30 segundos

Cualquier reclutador puede ver el funcionamiento real en vivo: subir una foto y ver el resultado procesado. No es un CRUD con UI bonita, es un pipeline de IA funcionando de extremo a extremo.

Stack inusual y diferenciador

Go en el backend + SvelteKit en el frontend es una combinación que aparece muy poco en portfolios junior. Demuestra criterio técnico propio y capacidad de aprender más allá de los caminos más trillados.

ML real, no decorativo

EasyOCR + clasificador scikit-learn no es una demo de "Hello World con TensorFlow". Es un pipeline de inferencia con un modelo entrenado, servido via FastAPI y consumido desde Go.

02 — Tecnologías

Stack Tecnológico

Cada tecnología elegida tiene una justificación concreta. No hay over-engineering ni tecnologías elegidas por moda sin respaldo.

SK

SvelteKit 2 + TypeScript

Meta-framework con el mayor índice de satisfacción de desarrolladores en 2026. Compila a JavaScript vanilla, sin runtime de 40KB. File-based routing, SSR nativo, DX superior a React para equipos pequeños.

Go

Go 1.22 — Gin + GORM

Backend altamente concurrente con goroutines para procesamiento asíncrono de imágenes. Gin como HTTP router minimalista. GORM para ORM sobre PostgreSQL. JWT middleware para autenticación.

ML

Python 3.11 — FastAPI + EasyOCR

Microservicio de inferencia independiente. EasyOCR extrae texto de imágenes (multilingüe, sin entrenamiento propio). Clasificador Random Forest con scikit-learn categoriza el gasto. Modelo serializado con joblib.

PG

PostgreSQL 16

Base de datos principal. Almacena usuarios, recibos, transacciones y presupuestos. JSONB para datos variables del OCR. Migraciones gestionadas con golang-migrate.

RD

Redis 7

Cola de trabajos asíncronos para el procesamiento de imágenes. Caché de sesiones JWT. Pub/Sub para notificaciones WebSocket. Previene bloqueos en el handler HTTP durante el OCR.

Tw

Tailwind CSS 4

Utilidades CSS para el frontend SvelteKit. Integración nativa con Vite. Design tokens centralizados en CSS variables. Consistencia visual sin CSS custom complicado.

Lc

Layerchart (D3)

Librería de gráficos nativa para Svelte, construida sobre D3. Dashboard financiero con gráficos de barras por categoría, líneas de evolución mensual y donut de distribución.

CI

GitHub Actions + Docker

Pipeline de CI/CD con tests automáticos en cada PR. Docker Compose para entorno local unificado (Go + Python + PostgreSQL + Redis en un solo comando). Deploy en Railway.

03 — Arquitectura

Diseño del Sistema

Arquitectura de microservicios ligera con tres capas diferenciadas: presentación, lógica de negocio y servicio de inferencia ML. La comunicación es asíncrona por diseño.

Capa de presentación — Navegador

Dashboard de gastos Upload de recibo Historial + filtros Gestión de presupuesto Auth (login / registro)
REST / JSON · WebSocket (notificaciones en tiempo real)

Capa de lógica — Backend Go

Auth handler (JWT) Receipt handler Image worker (goroutine) Finance service WS notifier
HTTP interno · Redis pub/sub

Servicio ML — Python FastAPI

EasyOCR (extracción texto) RF Classifier (categoría) Parser (importe + fecha)

Capa de datos

PostgreSQL (persistencia) Redis (queue + cache)

Flujo de procesamiento de un recibo

paso 01

Upload

Usuario sube imagen vía drag-and-drop o selector de archivo

paso 02

Enqueue

Go recibe imagen, la persiste en S3/disco, encola jobId en Redis. Responde 202 Accepted inmediatamente

paso 03

OCR + ML

Worker goroutine consume job, llama al ML Service via HTTP, recibe texto + categoría + importe

paso 04

Persist

Resultado se guarda en PostgreSQL. Se publica evento en Redis pub/sub

paso 05

Notify

WS notifier envía el recibo procesado al navegador. Dashboard se actualiza sin recargar

05 — Componentes

Estructura de Componentes

División clara entre frontend SvelteKit y backend Go. Los contratos de API en OpenAPI permiten que ambos desarrolladores trabajen en paralelo desde el día uno.

Frontend — SvelteKit / Svelte

  • +layout.svelteShell global: sidebar, topbar, WebSocket listener
  • +page.svelte (dashboard)Stats cards, gráfico mensual, lista recientes
  • +page.svelte (upload)Dropzone, preview imagen, estado del job en tiempo real
  • +page.svelte (history)Tabla paginada, filtros por categoría y fecha
  • +page.svelte (budget)Barras de progreso por categoría, edición inline
  • ReceiptCard.svelteTarjeta de recibo con estado (pending/done/error)
  • CategoryBadge.sveltePill coloreado por categoría de gasto
  • UploadDropzone.svelteÁrea drag-and-drop con validación de tipo/tamaño
  • SpendingChart.svelteWrapper de Layerchart con datos de la store
  • BudgetBar.svelteBarra de progreso con alerta al superar 80%
  • stores/transactions.tsSvelte store reactivo con caché local
  • stores/socket.tsGestión del WebSocket y eventos entrantes
  • lib/api.tsCliente HTTP tipado que consume el backend Go

Backend — Go (Gin)

  • handlers/auth.goRegister, login, refresh token, logout
  • handlers/receipts.goUpload, get by ID, list con paginación
  • handlers/transactions.goCRUD, filtros, aggregaciones mensuales
  • handlers/budgets.goCrear/actualizar presupuesto por categoría
  • handlers/ws.goEndpoint WebSocket, gestión de conexiones
  • workers/image.goWorker goroutine: consume Redis, llama ML, persiste
  • services/ml_client.goCliente HTTP hacia FastAPI de Python
  • services/finance.goCálculo de totales, categorías, alertas
  • middleware/auth.goValidación JWT en cada ruta protegida
  • models/user.goStruct User + métodos GORM
  • models/receipt.goStruct Receipt con enum de status
  • models/transaction.goStruct Transaction con categoría
  • db/migrations/Archivos SQL versionados con golang-migrate

ML Service — Python FastAPI

routers/inference.py

Endpoint POST /analyze que recibe la imagen como multipart/form-data. Orquesta OCR + clasificación y devuelve JSON con todos los campos extraídos.

services/ocr.py

Wrapper sobre EasyOCR. Preprocesa la imagen (resize, contraste), ejecuta la extracción de texto y devuelve líneas ordenadas por posición Y.

services/classifier.py

Carga el modelo model.joblib en startup. Vectoriza el texto con TF-IDF y predice la categoría. Confianza mínima del 60%, si no devuelve "otros".

services/parser.py

Extrae importe (regex sobre patrones €XX,XX), fecha (dateutil.parser) y nombre del comercio (primera línea del OCR, normalizada).

training/train.py

Script de entrenamiento del clasificador. Dataset sintético de 800 muestras por categoría. Exporta el pipeline TF-IDF + Random Forest a model.joblib.

schemas/response.py

Pydantic models para la respuesta: amount, merchant, date, category, confidence, raw_text.

07 — CI/CD y Colaboración

Pipeline y Flujo Git

GitHub Flow para dos personas: solo main como rama estable y feature branches de corta vida. Cada PR requiere revisión del compañero antes de mergear.

Estructura de ramas

main Siempre deployable. Protegida, requiere PR + CI verde
feat/auth-jwt Feature nueva. Vida máxima: 3-5 días
feat/upload-dropzone Feature nueva en paralelo (persona B)
fix/ocr-timeout Bugfix urgente, mergea directo con PR small
chore/update-deps Mantenimiento, sin revisión obligatoria

División por dominio

Persona A — Backend + ML

Backend Go (handlers, workers, servicios), ML Service Python, contratos OpenAPI, migraciones de base de datos, tests de backend.

Persona B — Frontend

SvelteKit (páginas, componentes, stores), integración API con msw en local, dashboards Layerchart, tests Vitest y Playwright E2E.

Punto de encuentro: OpenAPI Spec

Se define al inicio de cada fase. Persona B trabaja contra MSW mock mientras A implementa el backend real. Sin bloqueos.

Pipeline de GitHub Actions

on: push PR

lint Go test Go (unit) lint Python test Python (pytest) lint Svelte test Vitest

on: PR to main

integration tests (docker) Playwright E2E build check SvelteKit

on: merge main

docker build & push deploy Railway (Go + Python) deploy Railway (SvelteKit) run DB migrations
